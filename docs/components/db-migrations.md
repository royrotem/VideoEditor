# Component: DB / Migrations (Alembic)

> Schema migrations for the Postgres database, managed by Alembic.

## Purpose

Keep the production database schema in lock-step with `Base.metadata`.
Every schema change ships as a numbered migration in
`backend/alembic/versions`.

## Layout

```
backend/
├── alembic.ini          # Alembic CLI config (DSN overridden by env.py)
└── alembic/
    ├── env.py           # imports Settings + Base.metadata
    ├── script.py.mako   # template for new migrations
    └── versions/
        └── 0001_initial_schema.py
```

## Public interface

```bash
# Apply every pending migration
uv run alembic upgrade head

# Roll back the last migration
uv run alembic downgrade -1

# Generate a new migration from model diffs (review before committing!)
uv run alembic revision --autogenerate -m "describe the change"
```

## Inputs

- `Settings.database_url_sync` (psycopg-based DSN).
- `app.db.base.Base.metadata` populated by importing `app.db.models`.

## Outputs

A migrated Postgres database.

## Dependencies

- `alembic`, `sqlalchemy`, `psycopg[binary]`.
- A reachable Postgres instance.

## Errors

Standard Alembic errors. Most commonly: model drift detected when
`alembic upgrade head` runs - regenerate the autogenerated migration and
review the diff manually.

## How to test

- Run `uv run alembic upgrade head` against the docker-compose Postgres
  to ensure the migration applies cleanly.
- Run `uv run alembic downgrade base && uv run alembic upgrade head` to
  verify the migration is reversible.

## Change log notes

- `0001_initial_schema.py` was hand-written rather than autogenerated to
  avoid bootstrap-time model-import gymnastics. Every subsequent
  migration should be autogenerated and then manually reviewed.
- Native `ENUM` types are created in `upgrade()` and dropped in
  `downgrade()` - the `checkfirst=True` flag keeps the migration
  idempotent if a previous run left them behind.
